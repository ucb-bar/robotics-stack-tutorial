# ModelBlaster + LLM lab: setting it up for a room

Every participant has a PYNQ board on the tutorial WiFi and an AWS seat, and works in the seat's
JupyterLab following `docs/MB_ATTENDEE.md`. This page is for the people who set up the room.

## How the pieces connect

The attendee's laptop talks to their seat's JupyterLab over HTTPS, and the seat talks to Bedrock (the
LLM). Separately, the board opens a reverse ssh tunnel to the same seat, and the seat uses that tunnel to
run each image on the board through an agent on the card.

The attendee reaches only their seat, at `https://<seat>/`. Caddy serves it on 443 and passes it to
JupyterLab on the seat's loopback. The attendee needs no ssh or key and does not have to be on the room
network.

The board dials out and nothing dials in. On boot, `iiswc-tunnel.service` works out the board's seat
from the board's own address (10.42.0.N is seat N, `aws-N.iiswc`, resolved by the tutorial router) and
opens a reverse tunnel with the seat key the card carries, so the seat's `localhost:19022` reaches the
board's sshd. The unit retries forever, so boards may power on before the seats exist.

The seat drives the board through a fixed set of verbs, not a shell. The lab runs
`ssh -p 19022 -i ~/.ssh/iiswc-board-agent xilinx@localhost '<verb>'`, and on the board that key is tied
to `/opt/iiswc/host/tunnel_agent.sh`, which accepts only its own verbs. For each image the lab calls:

1. `put zephyr.bin <bytes> <md5>`;
2. `run zephyr` (loads the 0x5A5A0038 bitstream, boots the image, captures the console);
3. `get console.out` and `get run.log`.

Root steps go only through the card's `tunnel_priv.sh`, so a compromised seat can't get a shell on a
board. Only the seat talks to the LLM, using the Bedrock key in `~/.config/iiswc/bedrock.env`, which can
call only one model.

Some of this is not in the repository. The tunnel and agent scripts and the `aws_*` scripts are on the
tutorial card image, the router's name table is on the router, and JupyterLab and Caddy are on the seat
image.

| credential | who holds it | used for |
|---|---|---|
| Jupyter passphrase | the attendee | laptop → their seat's JupyterLab |
| seat key (`iiswc-2026-tutorial.pem`) | every card, and instructors | board → seat (the tunnel); instructor → seat (setup) |
| board agent key (`~/.ssh/iiswc-board-agent`) | every seat | seat → board, restricted to the agent's verbs |
| Bedrock key | every seat, and the admin | seat → Bedrock, one model in one region, with a cutoff |

`mb` can also run on the board itself, over ssh from a laptop on the room WiFi. In that mode the board
reaches its seat with the card's `aws_pull.sh`/`aws_push.sh` and runs the images itself. Because it
loads the FPGA directly it needs root on the board, either passwordless sudo or the board password,
entered once.

## Setting it up

### 1. The LLM key

One Bedrock key serves every seat. It can call one model in one region and has a cutoff time
(`docs/BEDROCK.md`). An AWS admin creates it with `scripts/93_bedrock_key.sh create`.

### 2. The seats

Each seat needs the RISC-V toolchain, the TACIT spike, a Python venv, this repo and the key. Run these
from a workstation that has the built toolchain (`scripts/00_bootstrap.sh`):

    scripts/96_seat_mb_setup.sh --seats seats.txt --ssh-key <seat key> --jobs 8
    BEDROCK_SECRET_FILE=secrets/bedrock.env scripts/93_bedrock_key.sh distribute --seats seats.txt --ssh-key <seat key>

`seats.txt` has one `ubuntu@<seat public IP>` per line (`aws/bedrock/seats.example`). The
`aws-N.iiswc` names resolve only through the tutorial router. The setup prints one `ok` or `FAILED`
line per seat, with its log. Each seat receives about 1.9 GB, so for a large room it is faster to set
up one seat, snapshot it as the AMI, and then only distribute the key.

The seat setup also puts the lab's folder in JupyterLab (`~/work/modelblaster-llm-lab/`) with a README,
the notebooks, the walkthroughs, and `your-kernel/` for the attendee's own kernel. It never overwrites
the attendee's notebook or kernel. The notebooks are generated by
`notebooks/mb_lab/tools/build_notebooks.py`, and `notebooks/mb_lab/README.md` shows the folder layout.

### 3. The boards

There is nothing to do here. The tutorial card image carries the tunnel, the agent, the loader and the
0x5A5A0038 bitstream, and the agent does its root steps through the card's own `tunnel_priv.sh`. For the
tunnel to come up, a board only needs its seat in the router's name table (`aws-N.iiswc`).

### 4. Check

In a seat's terminal, `mb doctor` checks the seat, its board through the tunnel, and the LLM key, all on
one screen.

### 5. At the venue

`scripts/97_mb_venue_check.sh` checks the whole lab on one seat. Run it in a JupyterLab terminal. It
uses the attendee's own commands on that seat's board, takes about 5 minutes, and prints a PASS/FAIL
table for:

- `mb doctor`;
- a kernel from a recorded LLM run, replayed on the FPGA;
- `mb try` with the solution;
- a wrong kernel and a broken kernel, both refused before the board;
- the notebooks.

`--full` adds three drills (a trapping kernel, an unreachable board, and a broken LLM key), and `--live`
adds one live LLM run with the board in the loop. To check the whole room, run it from any machine that
has the seat key:

    scripts/97_mb_venue_check.sh --seats seats.txt --ssh-key <seat key> --jobs 8

This prints one PASS/FAIL line per seat, with its log.

## Fallbacks

| problem | what still works |
|---|---|
| Bedrock down, or the key past its cutoff | Handled automatically. `mb go` notices, falls back to replaying a verified kernel from a recorded run, and says so. Spike and the board still run for real, and `mb try` needs no LLM |
| a board or its tunnel down | Handled automatically. `mb go` falls back to spike only and says so, and `mb doctor` says why. `mb_lab_solved.ipynb` shows a complete recorded run |
| a kernel that traps or never ends | stopped on spike within 3 minutes and never sent to the board |
| the router's name service, when `mb` runs on the board | `MB_SEAT=<seat IP> ~/mb` |
| a seat not set up | `mb` says so and names `96_seat_mb_setup.sh` |
| an interrupted run | run it again. When `mb` runs on the board, `~/mb run <run>` redoes only the board step and `~/mb collect <run>` redoes the verdict |

## What to expect

A live `mb` run on maxpool2d_s8 takes 5 to 8 minutes. In 8 test runs the kernel was 3.6 to 19.7× faster
on the FPGA (6 of 8 above 14×) and always matched the reference bit for bit, and 2.9 to 11.7× of that
came from the MBP. A replay takes about 2 minutes, and so does each `mb try` attempt. With 60
simultaneous users we measured the load at under 1% of Bedrock's quota per account for the model
(`docs/BEDROCK.md` §5).
